# control-receiver（qpm接收端）

QuestPhoneMirror 的「接收端 + 控制端」QuickDock 插件：连上手机的发送端后实时显示手机画面，
并支持用鼠标反向操控真机。v1.2.0 起新增**加密通道**（ECDH + AES-256-GCM）、
**剪贴板双向同步**、**文件上传到手机**与**手机投屏统计**。

> **配套手机端（发送端）**：<https://github.com/parieses/QuestPhoneMirror>
> 手机端负责 MediaProjection 录屏 + H.264 硬编 + 推流，并用无障碍服务执行本插件回传的点击/滑动。
> 加密/统计/剪贴板/文件推送需手机端 **v0.11+**；旧版手机端自动回落明文，功能不受影响。

```
[手机 QuestPhoneMirror 发送端]                       [本插件（PC）]
   MediaProjection → MediaCodec(H.264)                TCP client 主动连接 45556
   ServerSocket :45556 ──── 视频/SCREEN_INFO ───────► 解析协议帧 → 归一化 AVCC
   UDP :45555 广播 QPM1|port|WxH ── 自动发现 ───────►   │
   无障碍服务执行 ◄──── TAP/SWIPE/TEXT/KEY ──────────  本机 WebSocket（仅 127.0.0.1）
                                                       ├─ controlPort    控制通道（命令/状态/日志）
                                                       └─ controlPort+1  视频流（H.264）
                                                              ▼
                                                      前端 WebCodecs 解码 → canvas 上屏
                                                      鼠标点击/拖拽 → control.tap/swipe

[前端 iframe] ──①本地直连 ws://127.0.0.1:controlPort──► 后端（首选：不经宿主，1ms 级往返）
              └─②宿主桥接 plugin:execute ─────────────► 后端（兜底：本地端口没绑上时用）
```

## 两条命令通道（v1.0.4 起）

后端是宿主按需拉起的独立进程，前端与它之间原本只有一条「宿主转发」的桥：
`iframe → postMessage(plugin:execute) → 宿主 → 后端子进程`。

问题是宿主的插件窗口是**可复用**的，而后端会被 `treeKill` 后重建；桥一旦失效，请求发出去
**既没有响应也不报错**，界面就会永远停在「正在启动…」（这正是 v1.0.3 用户实测到的现象）。

现在改成双通道，互为兜底：

| 通道 | 建立方式 | 特点 |
|---|---|---|
| ① 本地直连（首选） | 后端在 `initialize` 时就把控制通道 WS 绑在 `127.0.0.1:controlPort`，前端直接连 | 不依赖宿主桥；单程 1ms 级；同一通道同时承载命令、状态推送与日志 |
| ② 宿主桥接（兜底） | `plugin:execute` JSON-RPC | 本地端口没绑上（如被占用）时的唯一通道 |

前端还会：单条请求**从入队起算硬超时**、响应按「当前在途请求」独占接收、队列带看门狗强制释放、
页面恢复可见/获得焦点时自动重新同步 —— 任何一条通道挂掉都不会让界面卡死。
标题栏的「**重置**」按钮可以随时清空队列并重建直连。

## 构建与安装

```bash
cd control-receiver
go build -o control-receiver.exe .      # 交叉编译见仓库根 build.py
python ../build.py control-receiver     # 产出 dist/io-github-parieses-control-receiver-windows.zip
```

装到 QuickDock：**插件管理 → 从文件安装**（更新前先「托盘图标右键 → 退出」彻底结束主进程，
否则旧 exe 会被占用、重装仍是老版本）。

## 使用步骤

1. 手机打开 QuestPhoneMirror（<https://github.com/parieses/QuestPhoneMirror>），选「我是发送端」，
   授予录屏权限；若要能操作手机，再到系统设置里打开 **QPM 无障碍服务**（不开只能看、不能点）。
   ⚠️ 若发现**只有 QQ / 微信 / 相册页面发糊**，那是手机系统的「屏幕共享防护」在拦截，与你这条投屏链路无关，
   见「常见问题 → 关掉手机的『屏幕共享防护』」。
2. 保持发送端 App 在前台（后台运行权限建议一并放行），插件里点「启动接收」。
3. 插件默认勾选「自动发现」：监听 UDP 45555 广播，发现手机后自动连接；也可手动填写
   `手机 IP` + `端口(默认 45556)`。
4. **配对（v1.1.0 起，新版手机端强制）**：连上手机后，若局域网内只有一台发送端，会自动**免码直连**；
   否则画面区会弹出配对码输入框——把手机端发送页显示的 **6 位配对码** 输进去点「配对」，通过后才会出画面。
   配对码输错手机端会记失败，**连续 3 次失败会断开连接**，重新连接即可再试。
   若提示「发送端已拒绝本机连接」：是手机端「连接管理」的白名单里没有本机，去手机端勾选本设备
   （列表里显示为 `qpm接收端(主机名)`，由本插件每秒广播的 QPMR 宣告而来）后再重连。
5. **浏览/下载手机文件（v1.1.0 起）**：点底栏「**文件**」打开文件面板（需配对通过；手机端需先在发送页
   点「授予文件访问权限」）。点目录进入、点文件「下载」，文件保存到插件数据目录的 `downloads` 文件夹
   （`.part` 临时文件收齐后改名，同名自动加序号不覆盖），面板里可取消下载、一键打开下载目录，进度实时显示。
6. **上传文件到手机（v1.2.0 起）**：文件面板点「**⬆ 上传到手机**」选本机文件，经本地直连通道以 256KB
   分片推送到手机共享存储（只传文件名，落点由手机端决定，与它「接收文件」的位置一致），进度实时显示、
   可取消。二进制分片只能走本地直连，宿主桥接不可用时会明确提示。
7. **剪贴板同步（v1.2.0 起）**：点底栏「**剪贴板**」打开对话框——手机端复制文本会自动同步过来，
   点「复制到本机」即可粘贴到电脑；在输入框写文本「发送到手机」则写入手机剪贴板，手机上直接粘贴。
   需配对通过。
8. 画面出现后即可操作：**单击=点击，拖拽=滑动（松开鼠标时整段执行，拖动期间画面上有虚线轨迹），长按=长按，右键=返回，滚轮=上下滑动**；
   底部控制条可发送 返回/Home/多任务 按键，点「⌨ 文本」展开输入框后回车发送文本。
9. 控制指令（点击/滑动/按键/文本）**走本地直连 WebSocket**，不占用宿主的 RPC 队列、
   也没有 RPC 超时等待，往返在毫秒级；只有直连未就绪时才自动退回宿主通道。
   未配对时这些指令会被前端直接拦截并提示（发出去手机端也不会执行）。
10. **界面空间**（v1.0.5 起）：
   - 顶部「端口 / 手机地址」设置条**默认收起**，标题栏右侧一行摘要显示当前配置（`控制 24556 · 视频 24557 · 手机 自动发现`），
     需要改端口时点「**设置**」展开；
   - 点标题栏「**侧栏**」可收起右侧状态栏，收起后画面拿到全部窗口宽度；
   - 底栏固定单行：导航键常驻，文本输入按需展开，操作说明收进右下角「**?**」。
   - 竖屏画面受**窗口高度**限制（1440×2964 这类长屏尤其明显），所以省下的纵向空间直接等于更大的画面。
11. 点标题栏「**沉浸**」或按 **F** 键让画面占满窗口（**Esc** 退出）。沉浸模式下底栏不会消失，
   而是变成底部居中的**浮动控制条**（返回 / Home / 多任务 / 文本 / 退出沉浸都在）：
   鼠标一动就浮出来，3 秒无操作自动淡出，正在输入文本时不会隐藏。
12. 右侧栏提供诊断入口：**配对状态**（等待配对 / 已配对 / 已被拒绝）、**加密通道**（AES-256-GCM / 明文，
   v1.2.0）、**手机统计**（手机端每秒广播的分辨率·fps·码率·丢帧，v1.2.0）、
   **控制通道 / 最后指令**（看指令走的是本地直连还是宿主通道、最后一条指令的坐标）、
   **点击自检**（向屏幕中心发一次点击并观察画面是否刷新）、**重连手机**（重新请求关键帧）。
   等待画面时提示层会按秒计时，超过 3 秒会给出可执行建议。
13. 界面如果「卡住不动」，点标题栏「**设置**」展开后按「**重置通道**」：清空排队请求、重建本地直连、重新同步状态。

```

WS 命令: start（本地直连 id=3）        ← 走本地直连
```

有 `启动接收` 但没有 `已连接手机发送端` → 是手机侧的问题（没开投屏 / IP 变了 / 端口不对）。

## 端口设置与「端口建议」

插件主体提供**控制端口**输入框（`controlPort`），配套：

| 端口 | 默认 | 用途 |
|---|---|---|
| `controlPort` | **24556** | 本地控制通道 WebSocket（状态 / 日志 / 画面参数推送，JSON） |
| `streamPort` = `controlPort + 1` | 24557 | 本地视频流 WebSocket（H.264 二进制帧） |
| 手机端口 | 45556 | 连接手机发送端的 TCP 端口（自动发现时以广播值为准） |
| 发现端口 | 45555 | 手机 UDP 广播，插件只监听 |

- 两个本地端口**只绑定 `127.0.0.1`**，不对外暴露。
- 默认 24556 的理由：高位、避开 1–1023 特权端口；与 QuestPhoneMirror 的 45556 命名风格呼应但错开；
  `+1 = 24557` 留给本地视频流，两者互不冲突。
- 点「端口建议」由后端 `port.suggest` 实时探测，返回默认值 + 2~3 个候选，每项带理由：

  | 候选 | 理由 |
  |---|---|
  | 24556 | 推荐默认：高位区间，避开特权端口，且与 QuestPhoneMirror 的 45556 错开 |
  | 24566 | 高位空闲，与默认 24556 错开，便于同时开多个实例 |
  | 35556 / 14556 | 同上，跨度更大的备选 |

  探测规则：① 静态排除 1–1023 特权端口、45555/45556（QPM 已用）与
  21/22/23/25/53/80/110/143/443/3306/5432/6379/8080/8443/9000 等常见服务端口；
  ② 用 `net.Listen` 实测本机占用，且**要求 controlPort 与 controlPort+1 成对可用**；
  ③ 默认端口被占用时，自动从 24556 起顺延到第一对空闲端口并标注原因。
- 点击候选即写入输入框并落盘 `config.json`；服务在跑时会就地重启到新端口。

## 协议对接（严格对齐 QuestPhoneMirror `Proto.kt`）

单条 TCP 双向复用，统一帧格式 `[type:u8][length:u32 LE][body]`：

| type | 方向 | body |
|---|---|---|
| `0x01` VIDEO_FRAME | 手机→本插件 | `[pts:u64 LE][flags:u8][h264]`，flags bit0=关键帧 bit1=SPS/PPS |
| `0x20` SCREEN_INFO | 手机→本插件 | `[w:u32][h:u32][dpi:u32]`（**v1.1.0 起配对通过后才下发**） |
| `0x10` TAP | 本插件→手机 | `[x:f32][y:f32]`（手机屏幕绝对像素） |
| `0x11` SWIPE | 本插件→手机 | `[x1][y1][x2][y2][durMs:u32]` |
| `0x12` TEXT | 本插件→手机 | UTF-8 文本 |
| `0x13` KEY | 本插件→手机 | `[keycode:u32]`（4=返回 3=Home 187=多任务） |
| `0x14` PAIR | 本插件→手机 | UTF-8 配对码；**空 body = 免密直连请求**（仅当局域网只有一个发送端时被接受） |
| `0x15` PAIR_RESULT | 手机→本插件 | `u8`（1=成功 0=失败；连续失败 3 次手机端断开连接） |
| `0x16` FILE_LIST_REQ | 本插件→手机 | UTF-8 路径 |
| `0x17` FILE_LIST_RES | 手机→本插件 | UTF-8，条目 `\n` 分隔、字段 `\t` 分隔：`name\tisDir\tsize\tmtime` |
| `0x18` FILE_GET_REQ | 本插件→手机 | UTF-8 路径 |
| `0x19` FILE_DATA | 手机→本插件 | `[offset:u64][total:u64][flags:u8(eof)][chunk]` |
| `0x1A` FILE_ERROR | 手机→本插件 | UTF-8（如未授权、路径非法） |
| `0x1B` HELLO | 本插件→手机 | UTF-8 设备名（建连后**立即报送**，手机端「连接管理」据此展示是谁） |
| `0x1C` REJECT | 手机→本插件 | UTF-8 拒绝原因（如未在白名单），发送后即断开 |
| `0x1D` CLIPBOARD | 双向 | UTF-8 文本。手机→本插件 = 手机复制了内容（同步到电脑）；本插件→手机 = 写入手机剪贴板 |
| `0x1E` KEY_EXCHANGE | 双向 | X.509(SPKI) 编码的 EC(secp256r1) 临时公钥；**握手第一帧、永远明文**（见下节） |
| `0x1F` STATS | 手机→本插件 | `[fps:u16][bitrateBps:u32][w:u16][h:u16][dropped:u16]`，配对后每秒广播（侧栏「手机统计」） |
| `0x21` FILE_PUSH_REQ | 本插件→手机 | `[total:u64][文件名]`——只发文件名，手机端自行决定落点（共享存储根目录内） |
| `0x22` FILE_PUSH_DATA | 本插件→手机 | `[offset:u64][flags:u8(eof)][chunk]`，64KB 分片；短分片或空 eof 帧表示结束 |
| `0x23` FILE_PUSH_RES | 手机→本插件 | `[ok:u8][msg]`（ok=1 时 msg 为手机侧保存路径） |

**握手与门控（v1.1.0 起配对；v1.2.0 起加密，对齐 QPM 工作区 `Proto.kt`/`SecureChannel.kt`）**：

1. TCP 建连后**立即发 `KEY_EXCHANGE`**（本方 EC P-256 临时公钥，SPKI 编码，明文）——新版手机端的
   读取循环要求对端**首帧必须是 KE**，否则整条连接回落明文，加密无从建立；
2. 紧接着发 `HELLO`（设备名 `qpm接收端(主机名)`）→ 再发 `PAIR`（上次配对成功的码，或空码请求免密直连）；
3. **加密通道（v1.2.0，双方都支持时自动生效）**：互换 KE 后各自执行 ECDH → SHA-256 → AES-256 会话密钥。
   之后每个帧**只加密 body**（AES/GCM/NoPadding，128-bit tag），5 字节帧头保持明文；
   nonce = `[方向:u32 BE][计数器:u64 BE]`（手机→本插件 = 0，本插件→手机 = 1，杜绝重放/乱序），
   `seal` 与 socket 写出在同一把写锁内原子完成，保证计数器自增与线上顺序一致。
   解密失败（被篡改/密钥不匹配）立即断开。侧栏「加密通道」显示当前是否加密；
4. 手机端回 `PAIR_RESULT`：**通过前**不下发 `SCREEN_INFO`/视频帧、不执行任何控制帧、不响应文件请求；
5. 白名单门控在配对前：手机端「连接管理」取消勾选本机时，本插件会先收到 `REJECT`（原因）再被断开——
   界面浮层明确提示并引导去手机端重新勾选；
6. 兼容旧版手机端（无配对协议）：未收到配对响应却直接收到画面时，自动识别并按原方式继续；
   旧手机端同样不回应 KE，本插件预读 1.5 秒超时后自动回落明文（功能不受影响、只是不加密）。

发现：手机每秒向 `255.255.255.255:45555` 广播 `QPM1|<tcpPort>|<w>x<h>`（发送端宣告）；
本插件每秒向同端口广播 `QPMR|qpm接收端(主机名)`（接收端宣告），
使手机端「连接管理」在连接建立前即可扫描到本机、按 IP 预勾选白名单。两类 beacon 按前缀区分，互不干扰。

**关于 H.264 封装（实测结论）**：任务书假定视频载荷是 AVCC（4 字节大端长度前缀），
但实测 Android 14 / 1440×2964 设备上 MediaCodec 的 AVC 输出是 **Annex-B**（`00 00 00 01` 起始码），
SPS/PPS 由独立的 flags bit1 帧下发（内容为 `SPS+PPS+SPS+PPS`）。后端因此做**自动识别并统一归一化为 AVCC**：
- flags bit1 帧 → 抽出 SPS/PPS → 构造 `AVCDecoderConfigurationRecord`（avcC）与 `avc1.PPCCLL` codec 串下发前端；
- 普通帧 → 起始码转 4 字节长度前缀（本来就是 AVCC 的原样透传）；
- 若 IDR 帧内联了参数集（部分设备）→ 从帧内抽取并补出 avcC。

前端 `VideoDecoder.configure({codec:"avc1.xxxxxx", description:avcC})` 后，逐帧喂 AVCC 的
`EncodedVideoChunk`（`timestamp` 用 pts 微秒，key/delta 由 flags bit0 决定）。

## 命令（`plugin.execute` 的 `command`）

| 命令 | 入参 | 说明 |
|---|---|---|
| `start` | `{host?, port?, controlPort?, phoneHost?, phonePort?, autoDiscover?, discover?}` | 启动本地服务并连接手机；带 `controlPort`/`phoneHost` 时会**顺带落盘配置**（前端只发一次 RPC 即可完成「保存端口 + 启动」）；`host` 为空且 discover=autoDiscover 时走自动发现 |
| `stop` | — | 断开手机连接并停止发现 |
| `status` | — | 连接状态、分辨率、帧率/码率、端口、WS 客户端数、avcC、加密通道（`crypto`）、手机统计（`stats`）、下载/上传进度（`fileDl`/`filePush`）等 |
| `port.suggest` | — | 端口建议（含理由、可用性、推荐值） |
| `phone.reconnect` | — | 断开并重新连接手机（手机端每次接连接都会 `requestKeyFrame()`，是「等待画面 / 画面冻结」的恢复手段） |
| `control.tap` | `{x,y}` | 点击（手机屏幕像素） |
| `control.swipe` | `{x1,y1,x2,y2,durationMs}` | 滑动 |
| `control.text` | `{text}` | 输入文本 |
| `control.key` | `{keycode}` | 按键 |
| `pair` | `{code}` | 报送配对码（**空码=再次请求免密直连**）；成功时配对码落盘供同会话重连复用 |
| `file.list` | `{path?}` | 列出手机端目录（默认 `/sdcard`），返回 `name/isDir/size/mtime` 条目；需配对通过 |
| `file.get` | `{path}` | **异步**下载手机端文件到 `<数据目录>/downloads/`（`.part` 收齐后改名，同名加序号）；进度经控制通道广播 `{"t":"filedl",...}` |
| `file.cancel` | — | 取消进行中的下载（丢弃后续分片） |
| `file.push` | `{path}` | **异步**把本机文件推送到手机共享存储（64KB 分片；只发文件名，手机端决定落点）。进度/结果经控制通道广播 `{"t":"filepush",...}`。浏览器上传（File 对象无本机路径）改走控制通道二进制分片：`{"t":"filepush.begin","name","size"}` → 二进制数据帧 ×N → `{"t":"filepush.end"}`，后端原样转成 0x21/0x22，不经宿主的 JSON 通道 |
| `file.push.cancel` | — | 取消进行中的推送（协议内无取消帧，停止发送；手机端可能仍会保存已收到的部分） |
| `clipboard.send` | `{text}` | 把文本写入手机剪贴板（需配对通过）。反向（手机→电脑）：手机端复制的内容经 `0x1D` 同步过来，底栏「剪贴板」对话框查看、一键复制到本机 |
| `file.reveal` | — | 在资源管理器中打开下载目录 |
| `config.get` / `config.set` | `config.set`: `{controlPort?, phoneHost?, phonePort?, autoDiscover?}` | 读写 `config.json`（控制端口变更会就地重启本地服务；`pairCode` 由配对成功时自动写入） |
| `stream.pull` | `{since, maxChunks?, maxBytes?}` | **兜底**：轮询取流（WebSocket 不可用时启用） |

以上命令既可以通过宿主的 `plugin.execute` 调用，也可以**直接经本地控制通道 WebSocket 下发**
（载荷同形，把 `command` 换成 `t`，可带 `id`，回复是 `{"t":"res","id":..,"ok":true,"data":..}`）。
白名单：`start` / `stop` / `status` / `port.suggest` / `phone.reconnect` / `config.get` /
`config.set` / `stream.pull` / `control.*` / `pair` / `file.*` / `clipboard.send`；
另有两个传输层信令 `filepush.begin` / `filepush.end`（配合二进制数据帧上传文件，不属于 RPC 命令）。
不含任何本机文件、进程、shell 能力（`file.*` 只读已配对的手机、只写插件自己的 downloads 目录），
且只监听 `127.0.0.1`。

## 取流通道：WebSocket 优先，RPC 轮询兜底

1. **WebSocket（默认）**：前端连 `ws://127.0.0.1:<streamPort>/` 拿二进制视频帧
   （`[flags:u8][pts:u64 LE][avcc…]`），连 `<controlPort>` 拿命令/状态/日志，延迟最低。
2. **`stream.pull` 轮询**：若宿主 iframe 沙箱环境拦截了 WebSocket（或端口被占），
   前端 1.2 秒内未接通就会自动退化到轮询取流，界面右上角标签会显示当前通道。

控制指令（`control.tap/swipe/text/key`）同走本地直连的 `<controlPort>` 通道，延迟毫秒级；
直连未就绪时自动退回宿主通道。

## 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| 连上了但画面全黑 / 一直「等待画面… N 秒」 | 手机息屏或画面完全静止时 MediaProjection **不会产出新帧**，所以「已连接」不等于「有画面」。后端带**首帧看门狗**：2.5 秒一帧都没收到就自动重连（最多 3 次）以再次请求关键帧；也可手动点界面上的「**重连手机**」或提示层里的「重新请求画面」。仍然黑屏就先点亮手机屏幕、让画面有变化 |
| 连上后一直停在「等待配对」，不出画面 | v1.1.0 起新版手机端（v0.9+）**配对通过前不下发画面**。若局域网内只有一台发送端，插件会自动免码直连；有多台时画面区会弹出配对码输入框——输入手机端发送页显示的 **6 位配对码**点「配对」即可。侧栏「配对状态」会显示当前处于「等待配对 / 已配对 / 已被拒绝」哪种状态 |
| 配对码输错被断开 / 提示「配对失败」 | 手机端会记录失败次数，**连续 3 次失败会主动断开连接**。重新点「启动接收」或「重连手机」即可再次输入，配对成功前不会收到画面 |
| 提示「发送端已拒绝本机连接」 | 手机端「连接管理」的 **allowedHosts 白名单**已启用且不含本机 IP，手机端回 `REJECT` 后即断开。到手机端「连接管理」里勾选本设备（列表名 `qpm接收端(主机名)`，来自本插件每秒广播的 QPMR 宣告）再重连；白名单为空表示不限制 |
| 文件面板打不开 / 目录为空 / 下载报「未授权」 | ① 先确认**配对已通过**（文件请求受配对门控，未配对发不出去）；② 手机端需先在发送页点「**授予文件访问权限**」（MANAGE_EXTERNAL_STORAGE），未授权时手机会回 `FILE_ERROR`；③ 路径要合法（默认 `/sdcard`），手机端不认识的路径会直接报错 |
| 下载中途取消，文件去哪了 | 取消后已下载的分片被丢弃，残留的 `.part` 临时文件会保留在下载目录（`<数据目录>/downloads/`），不影响已完成的文件；同目录下同名文件会自动加序号，**不会互相覆盖** |
| 侧栏「加密通道」显示「明文」 | 手机端是旧版本（未回应 `KEY_EXCHANGE`）：控制/文件照常工作，只是帧不加密。双方都是新版时显示 **AES-256-GCM**——此时只有帧体加密、5 字节帧头仍明文（协议如此，用于寻址） |
| 上传文件报「本地直连不可用」 | 二进制分片只能走本地直连 WebSocket（宿主桥是 JSON 文本通道）。点「重置通道」或换个控制端口重试；`file.push` 路径直推（RPC）不受此限 |
| 上传中途取消，手机端文件去哪了 | 协议内没有取消帧：已发出的分片手机端可能仍在写入并保存为**部分文件**。以后端广播的最终结果（`{"t":"filepush","phase":"done"}`）为准 |
| 「剪贴板」对话框收不到手机复制的文本 | ① 需配对通过；② 手机端 v0.11 起才广播 `CLIPBOARD`；③ 非文本内容（图片等）不会同步 |
| 点了画面没反应 / 只有部分操作有效 | 先点右侧栏「**点击自检**」：它向屏幕中心发一次点击并观察画面是否刷新。① 有刷新 → 指令链路通，问题在点击位置没有可响应元素；② 完全没刷新 → 指令已发出但手机没执行，绝大多数是手机端 **QPM 无障碍服务未开启**（设置 → 无障碍 → 已下载的服务 → QPM 控制服务），其次是被系统限制。右侧栏的「控制通道 / 最后指令」可以确认指令是否真的发出（显示坐标即为已发出） |
| **能点击，但怎么拖都划不动** | v1.2.1 已修：旧版把一次拖拽按 40ms 切成十几像素的短滑动连发，手机端每条 SWIPE 都是 `dispatchGesture` 的一次完整手势（按下→抬起），位移低于系统 touch slop（约 8dp）、且切片之间手势互相打断被静默丢弃，所以永远滚不动。现在拖动只记轨迹、**松开鼠标时整段发一条**滑动（时长取真实拖动时长）。升级后仍是旧行为 → 见下一行「升级插件后仍是旧行为」。临时替代：**滚轮**直接上下滑（每格一次 240ms 滑动），或点完再手势按钮 |
| 拖动时要松开鼠标才动，能实时跟手吗 | 跟手需要手机端支持「一段手势持续续接」（`StrokeDescription` 的 `willContinue` / `continueStroke`），当前协议只有「一条 SWIPE = 一次完整手势」，所以拖动期间画面不会跟着动、松手才执行。要实时滚动用**滚轮**；后续给协议加 `drag.begin/move/end` 后即可实时跟手 |
| 停止再启动时画面「秒出」，第一次却很慢 | 手机端每次接受连接都会 `requestKeyFrame()`，但**静止画面下编码器没有输入帧就不会产出 IDR**。第一次连接要等到画面有变化才出图；此后的连接因为画面已在滚动会立刻出图。想让首帧更快：连接后动一下手机屏幕（点亮/滑动） |
| `监听 UDP 45555 失败` | 该端口已被其它程序占用（如另一个接收端实例），改用「手动填写手机 IP」 |
| `控制端口 xxx 无法监听` | 端口被占用，点「端口建议」换一个候选端口（面板右上角「×」关闭，选中候选后会自动收起） |
| 插件日志里出现「插件崩溃，尝试自动重启」 | 宿主在插件窗口关闭后仍会惰性复活后端，后端随 stdin 关闭正常退出，宿主会记为一次「崩溃」并重启——属宿主行为，打开插件窗口后即稳定 |
| 点了「启动接收」后界面一直停在「正在启动…」 | 宿主 → 插件的命令桥失效（宿主会复用插件窗口、并可能在关窗时 `treeKill` 掉后端再重建）。v1.0.4 起前端会**直接连本地端口**，不再依赖这条桥；仍遇到时展开「**设置**」点「**重置通道**」；若日志里连 `RPC 命令`/`WS 命令` 都没有，把 QuickDock 从托盘完全退出后重开 |
| 画面太小 / 周围空得慌 | 竖屏画面只受**窗口高度**限制，横向本来就有富余。三重省空间：① 设置条默认收起（点「设置」才展开）；② 点「**侧栏**」收起右侧状态栏；③ 点「沉浸」或按 **F** 让画面占满窗口。窗口本身也可以拉高 |
| 沉浸模式下找不到返回 / Home / 多任务 | v1.0.5 起沉浸模式**不再隐藏底栏**，底栏变成屏幕底部居中的浮动控制条（鼠标移到底部即浮出，3 秒无操作淡出）。如果刚好淡出了，动一下鼠标即可 |
| 升级插件后仍是旧行为 | QuickDock 主进程还在跑，插件 exe 被锁定；托盘右键退出后再重装 |
| **只有 QQ / 微信 / 相册 / 支付类页面发糊，别的页面清晰** | 这是手机系统的「**屏幕共享防护**」（厂商防诈骗功能）在起作用：它一旦检测到有应用在录屏/投屏，就会把社交、相册、金融类应用的画面**模糊化**后再交给录屏接口。**插件收到的已经是被系统模糊过的画面，无从还原** —— 右侧栏「实际编码帧」此时仍等于「手机屏幕」，就是最好的证据。处理办法见下一节 |
| 手机转了横屏，画面没跟着横 / 点击位置错位 | v1.0.6 起前端**以画面方向为准**自动校正：解码帧变成 `2964×1440` 就会自动把控制坐标切成横屏映射，侧栏「手机屏幕」也会标注「横 / 竖」。若「实际编码帧」**仍是** `1440×2964`，说明手机端没有重建编码器（VirtualDisplay 没跟着旋转），点「**重连手机**」强制刷新一次；仍不行就需要手机端在屏幕旋转时重建编码器 |
| 手机横屏后画面挤在中间一条窄横条、面积很小 | v1.0.9 起方向**永远跟随手机真实方向**、且默认「**⬔ 智能**」铺满方式：手机横竖与窗口横竖同方向时，自动等比放大铺满窗口（只裁极少溢出）；方向不一致时自动退回「完整」(contain)，只留黑边、**不丢内容、绝不把内容转反**。把接收窗口拉到和手机同方向（竖屏手机用竖窗、横屏手机用横窗）就能自然铺满 |
| 竖屏手机在全屏（横屏窗口）里显示成横屏 / 方向被转反了 | v1.0.9 已**彻底移除内容旋转**：方向永远 = 手机真实方向，竖屏手机永远显示竖屏、横屏永远显示横屏，绝不转反。旧的「↻ 旋转填满」按钮已升级为「**⬔ 智能 / ⤢ 填满 / ⤡ 完整**」三态循环 |
| 全屏 / 窗口方向和手机不一致，画面偏小、四周留黑边 | 方向一致时智能模式自动铺满、无黑边；方向不一致时智能模式**自动退回完整显示**（留黑边、不丢内容）。此时点底部按钮切到「**⤢ 填满**」可**强制等比放大铺满窗口、超出部分裁掉**——手机竖持看横屏视频（画面居中带黑边）时用它，黑边正好被裁掉、画面铺满整个窗口；切「**⤡ 完整**」看全貌；再点回到「⬔ 智能」。三种方式点击坐标都精准 |

### 关掉手机的「屏幕共享防护」

投屏时若手机屏幕上弹出一个**红色提示按钮**，点它并选「**继续共享**」即可**单次放行**当前这次共享（不改系统设置，最省事）。

要**永久关闭**，按机型走：

| 机型 | 路径 |
|---|---|
| 小米 / Redmi（MIUI 14、澎湃 OS） | 设置 → 搜「**电诈防护**」（或 设置 → 安全 → 电诈防护）→ **屏幕共享防护** → 关闭。若无效，再看 设置 → 更多设置 → 开发者选项 → **停用屏幕防护共享** |
| 华为 / 荣耀 | 先连点「版本号」7 次开开发者选项，再 设置 → 系统和更新 → 开发人员选项 → **停用屏幕防护共享**；若有「屏幕共享编码优化」可设为**兼容模式** |
| OPPO / 一加 / realme | 连点「版本号」7 次开开发者选项 → 设置 → 其他设置 → 开发者选项 → **停用屏幕防护共享**；同页若有「投屏分辨率」可设为 **1080P** |
| 原生 Android 15 / Pixel | 开发者选项 → **停用屏幕共享防护 / Disable screen share protections** |

> 关掉之后，录屏/投屏会**完整显示**密码、验证码、聊天内容。演示或调试完建议重新打开。

### 「画面糊」怎么定位到具体哪一层

右侧栏从 v1.0.6 起把两个分辨率并排显示，配合日志可以三步定位：

| 现象 | 结论 |
|---|---|
| 「实际编码帧」**小于**「手机屏幕」，日志出现 `被放大 N× 显示` | 手机端**降了编码分辨率**（编码器压力大 / 省电模式），这是糊的直接原因 |
| 两者**一致**，但 QQ/微信页面仍糊、其他页面清晰 | **系统「屏幕共享防护」**（见上一节），或 App 自身的高斯模糊效果 |
| 两者一致、码率长期顶格、一滚动就糊 | **码率不够**：图文密集页面的压缩效率远低于桌面大色块 |
| 「显示缩放」很低（如 `25%`） | 画面被缩到 1/4 显示，小字号界面天然发虚——把窗口拉高或用沉浸模式可缓解 |

## 与 QuestPhoneMirror 的联动要点

- 本插件**不修改手机端**，只作为接收端：连接它的 `ServerSocket(45556)`，并在同一条连接上回写控制帧。
- **配对与白名单（v1.1.0 / 手机端 v0.9+）**：手机端 `CastService.acceptLoop` 的处理顺序是
  ① `isReceiverAllowed` 白名单检查（名单非空且不含本机 IP → 回 `REJECT` 后断开）；
  ② 读 `HELLO` 登记设备名（「连接管理」据此显示是谁）；
  ③ 读 `PAIR` 做配对门控——**通过前**不下发 `SCREEN_INFO`/视频帧、不执行任何控制帧、不响应文件请求；
  连续配对失败 3 次断开连接；空配对码（免密直连）仅当局域网只有一个发送端时被接受。
- **加密通道（v1.2.0 / 手机端 v0.11+）**：手机端发送器 `CastService.readLoop` 要求**对端首帧必须是
  `KEY_EXCHANGE`**，否则整条连接回落明文——所以本插件建连后第一帧就发 KE（本方 EC P-256 临时公钥，
  SPKI 编码，明文），再发 HELLO/PAIR。双方互换 KE 后 ECDH → SHA-256 → AES-256-GCM（只加密 body，
  nonce 带方向位与计数器）。手机端不回应 KE 时 1.5 秒预读超时回落明文，旧手机端完全兼容。
- **手机统计（0x1F STATS）**：配对后手机端每秒广播编码分辨率/fps/码率/丢帧，侧栏「手机统计」实时显示，
  与本地解码帧率对照即可区分「手机端产得少」和「本地解码/显示跟不上」。
- **剪贴板（0x1D CLIPBOARD）双向**：手机端复制文本 → 广播到接收端（前端对话框展示、一键复制到本机）；
  接收端 `clipboard.send` → 写入手机剪贴板。两端都有 `clipSyncSuppress`/状态位防止回环。
- **文件能力**：v1.1.0 的下载（`FILE_LIST_REQ`/`FILE_GET_REQ`）需手机端授予「文件访问权限」，
  未授权/路径非法时回 `FILE_ERROR`；v1.2.0 新增推送（`FILE_PUSH_REQ/DATA/RES`）：只发文件名，
  手机端 `FileRelay.resolveWritable` 把落点约束在共享存储根目录内，64KB 分片、短分片即 eof。
  浏览器上传走「控制通道二进制分片 → 后端中转」：前端把 File 切成 256KB 二进制帧经本地直连 WS 发来，
  后端原样转成 0x22（免 base64、免落盘中转）。
- `SCREEN_INFO` + `requestKeyFrame()` 现在在 `onPaired`（配对通过）时才下发，因此**中途连入也能在
  配对后 1 秒内拿到关键帧**；`KEY_I_FRAME_INTERVAL=1` 保证每秒至少一个 IDR。
  ⚠️ 注意 `SCREEN_INFO` **仍只在配对时发一次**：手机旋转后多数机型不会重发，所以前端从 v1.0.6 起
  改用「解码帧方向」作为屏幕方向的权威来源，必要时把 `SCREEN_INFO` 横竖对齐后再映射控制坐标。
- 控制帧由手机端 `CastService.readLoop` 读取，交给无障碍服务 `QpmControlService` 执行
  （`dispatchGesture`，Android 7.0+ 无需 root）。坐标是**屏幕绝对像素**，前端用 `SCREEN_INFO` 的 w/h
  把画布坐标按比例换算后再发；v1.1.0 起这些帧在**配对通过前**手机端不会执行（前端也会先拦截并提示）。
  ⚠️ **一条 SWIPE 帧 = 一次完整手势**（按下→移动→抬起），手机端目前没有 `willContinue` 续接能力：
  所以前端 v1.2.1 起把一次拖拽合成**一条**滑动、在松手时发出，而不是按住期间切片连发——
  切片每段只有十几像素，低于系统 touch slop（约 8dp），且手势串行执行时后一片会被静默丢弃，
  这正是 v1.2.0 及以前「能点击、怎么拖都划不动」的根因。
  未配对/无无障碍服务时手机端 `dispatchControl` 会丢弃并在 logcat 限流打印提示（`QpmControlService` 标签）。
- **文件能力（v1.1.0）**：`FILE_LIST_REQ` / `FILE_GET_REQ` 由手机端在配对通过、且用户已授予
  「文件访问权限」后响应；未授权/路径非法时回 `FILE_ERROR`（UTF-8 原因），插件把它透到界面。
- **双 beacon 协同**：手机每秒广播 `QPM1|port|WxH`（发送端宣告，插件据此自动发现）；
  插件每秒广播 `QPMR|设备名`（接收端宣告，手机端「连接管理」据此在连接前列出本机、按 IP 预勾白名单）。
  两类 beacon 同在 UDP 45555，按前缀区分，互不干扰。
- 手机端每个客户端队列深度为 3（满则丢最旧帧，优先保延迟）；本插件的视频通道同样是
  「队列满丢最旧」，两侧策略一致，网络抖动时优先牺牲画质而不是延迟。
